## Начало работы

### Предварительные требования

Перед началом участия убедитесь, что у вас есть:

1. **Godot Engine 4.x** (последняя стабильная версия)
2. **Git** для контроля версий
3. **Учетная запись Supabase** (для функций базы данных)
4. Базовые знания GDScript
5. Знакомство с редактором Godot

### Настройка среды разработки

1. Сделайте форк репозитория на GitHub
2. Клонируйте свой форк локально:
```bash
git clone https://github.com/YOUR_USERNAME/universo-platformo-godot.git
cd universo-platformo-godot
```

3. Добавьте upstream-репозиторий:
```bash
git remote add upstream https://github.com/teknokomo/universo-platformo-godot.git
```

4. Скопируйте файл окружения и настройте:
```bash
cp .env.example .env
# Отредактируйте .env, добавив свои учетные данные Supabase
```

5. Откройте проект в редакторе Godot:
```bash
godot --editor project.godot
```

## Рабочий процесс разработки

### 1. Найдите или создайте Issue

- Просмотрите существующие [Issues](https://github.com/teknokomo/universo-platformo-godot/issues)
- При создании нового issue следуйте [Рекомендациям по Issues](#рекомендации-по-issues)
- Прокомментируйте issue, чтобы заявить о работе над ним перед началом

### 2. Создайте ветку функции

```bash
git checkout -b feature/your-feature-name
```

Соглашения об именовании веток:
- `feature/feature-name` - Новые функции
- `fix/bug-description` - Исправления ошибок
- `docs/update-description` - Обновления документации
- `refactor/component-name` - Рефакторинг кода

### 3. Внесите изменения

- Следуйте нашим [Стандартам кодирования](#стандарты-кодирования)
- Пишите чистый, документированный код
- Тщательно тестируйте свои изменения
- Делайте частые коммиты с понятными сообщениями

### 4. Держите ветку обновленной

```bash
git fetch upstream
git rebase upstream/main
```

### 5. Отправьте Pull Request

- Отправьте свою ветку в свой форк
- Создайте Pull Request, следуя [Рекомендациям по PR](#рекомендации-по-pull-request)
- Дождитесь ревью и устраните замечания

## Стандарты кодирования

### Руководство по стилю GDScript

Мы следуем [официальному руководству по стилю GDScript](https://docs.godotengine.org/en/stable/tutorials/scripting/gdscript/gdscript_styleguide.html) с этими дополнениями:

#### Организация файлов

```gdscript
extends Node
## Краткое описание класса
##
## Подробное описание, предоставляющее контекст и информацию об использовании.
## Допускается несколько абзацев.

# Сначала константы
const MAX_SPEED := 100
const DEFAULT_NAME := "Player"

# Перечисления
enum State { IDLE, RUNNING, JUMPING }

# Экспортируемые переменные
@export var speed := 50.0
@export var health := 100

# Публичные переменные
var is_alive := true
var score := 0

# Приватные переменные (с префиксом подчеркивания)
var _internal_state := State.IDLE

# Переменные onready
@onready var sprite: Sprite2D = $Sprite2D

# Сигналы
signal health_changed(new_health: int)
signal player_died

# Встроенные виртуальные методы
func _ready() -> void:
	pass

func _process(delta: float) -> void:
	pass

# Публичные методы
func take_damage(amount: int) -> void:
	health -= amount
	health_changed.emit(health)

# Приватные методы
func _update_internal_state() -> void:
	pass
```

#### Соглашения об именовании

- **Переменные**: `snake_case`
- **Константы**: `UPPER_CASE`
- **Функции**: `snake_case`
- **Классы**: `PascalCase`
- **Сигналы**: `snake_case`
- **Приватные члены**: `_prefixed_with_underscore`

#### Указания типов

Всегда используйте указания типов для лучшей производительности и обнаружения ошибок:

```gdscript
func calculate_damage(base_damage: int, multiplier: float) -> int:
	return int(base_damage * multiplier)
```

#### Документация

Используйте `##` для комментариев документации, которые появляются в редакторе:

```gdscript
## Вычисляет общий урон с модификаторами
##
## Принимает базовый урон и применяет множители и сопротивления
## для расчета финального значения урона.
##
## @param base_damage Начальное значение урона
## @param multiplier Множитель урона (1.0 = без изменений)
## @return Финальное вычисленное значение урона
func calculate_damage(base_damage: int, multiplier: float) -> int:
	return int(base_damage * multiplier)
```

### Организация сцен

- Одна главная сцена на функцию/компонент
- Логически группируйте связанные узлы
- Используйте описательные имена узлов
- Следуйте структуре директорий проекта

### Структура файлов

```
packages/{feature}/base/
├── scenes/           # Файлы сцен (.tscn)
├── scripts/          # Файлы GDScript (.gd)
├── resources/        # Файлы ресурсов (.tres, .res)
├── assets/           # Ресурсы, специфичные для функции
├── plugin.cfg        # Конфигурация плагина
├── plugin.gd         # Точка входа плагина
├── README.md         # Документация на английском
└── README-RU.md     # Документация на русском
```

## Стандарты документации

### Двуязычная документация

Вся документация должна быть предоставлена на английском и русском языках:

1. **Сначала создайте английскую версию** (например, `README.md`)
2. **Создайте идентичную русскую версию** (например, `README-RU.md`)
3. **Поддерживайте одинаковую структуру и количество строк** в обеих версиях
4. Следуйте рекомендациям в `.github/instructions/i18n-docs.md`

### Требования к документации

Каждый пакет должен включать:
- `README.md` - Документация на английском
- `README-RU.md` - Документация на русском (идентичная структура)
- Комментарии кода для публичных API
- Примеры использования
- Рекомендации по интеграции

### Стиль комментариев

```gdscript
## Документация публичной функции
## Допускается несколько строк
func public_function() -> void:
	pass

# Комментарий к приватной реализации
func _private_function() -> void:
	# Встроенный комментарий, объясняющий сложную логику
	var result = complex_calculation()
```

## Разработка пакетов

> **⚠️ ОБЯЗАТЕЛЬНО**: ВСЯ функциональность функций ДОЛЖНА быть реализована как пакеты в директории `packages/`. Это обязательное архитектурное требование. Реализация вне `packages/` нарушает основные принципы проекта.

### Требования к архитектуре пакетов

**Конституционное требование**: Каждая функция должна быть организована в самодостаточные пакеты с:
- Функциональностью фронтенда в `packages/{feature}-frt/base/`
- Функциональностью бэкенда в `packages/{feature}-srv/base/`
- Общим кодом в выделенных пакетах (например, `packages/universo-types/`)
- БЕЗ логики функций в корневых директориях `scripts/` или `scenes/`

**Будущая миграция**: Пакеты будут извлечены в отдельные репозитории по мере созревания проекта. Проектируйте свои пакеты так, чтобы их можно было развернуть независимо.

### Создание нового пакета

1. **Создайте структуру директорий**:
```bash
mkdir -p packages/{feature}-frt/base/{scenes,scripts}
mkdir -p packages/{feature}-srv/base/{scripts,api}
```

2. **Добавьте конфигурацию плагина** (`plugin.cfg`):
```ini
[plugin]

name="Feature Name"
description="Description of the feature"
author="Universo Platformo"
version="0.1.0"
script="plugin.gd"
```

3. **Создайте точку входа плагина** (`plugin.gd`):
```gdscript
@tool
extends EditorPlugin

func _enter_tree() -> void:
	print("Feature Plugin: Enabled")

func _exit_tree() -> void:
	print("Feature Plugin: Disabled")
```

4. **Добавьте файлы README**:
   - Создайте `README.md` (английский)
   - Создайте `README-RU.md` (русский, идентичная структура)

5. **Реализуйте функциональность**:
   - Добавьте сцены в `scenes/`
   - Добавьте скрипты в `scripts/`
   - Задокументируйте все публичные API

### Интеграция пакетов

Пакеты интегрируются через:
- **Автозагрузки**: Глобальные менеджеры (Config, DatabaseManager, NetworkManager)
- **Сигналы**: Событийно-ориентированная коммуникация
- **Прямые ссылки**: Когда это уместно

## Тестирование

### Ручное тестирование

1. Откройте проект в редакторе Godot
2. Включите свой плагин в Настройки проекта → Плагины
3. Протестируйте функциональность через UI
4. Проверьте сетевые функции в режиме клиент/сервер
5. Проверьте операции с базой данных

### Запуск тестовых сцен

```bash
godot --path . scenes/your_test_scene.tscn
```

### Тестирование режима сервера

```bash
godot --headless --path . scenes/server.tscn
```

## Процесс ревью кода

1. Отправьте свой PR с полной документацией
2. Будут запущены автоматические проверки
3. Мейнтейнеры проверят ваш код
4. Оперативно устраните замечания
5. После одобрения ваш PR будет объединен
