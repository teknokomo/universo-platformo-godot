# Архитектура Universo Platformo Godot

## Обзор

Этот документ описывает архитектуру Universo Platformo Godot, объясняя проектные решения, паттерны и общую структуру системы.

## Принципы проектирования

### 1. Модульная архитектура (ОБЯЗАТЕЛЬНО)

**КРИТИЧЕСКИ ВАЖНО**: Система ДОЛЖНА быть организована в независимые, переиспользуемые пакеты в директории `packages/`. Каждая функция самодостаточна с четкими границами и интерфейсами.

**Требование реализации**: ВСЯ функциональность (кроме общих файлов запуска/сборки в корне репозитория) ДОЛЖНА быть реализована внутри `packages/`. Реализация функциональности вне `packages/` СТРОГО ЗАПРЕЩЕНА и нарушает основные архитектурные принципы проекта.

**Преимущества модульной структуры**:
- Независимая разработка и тестирование функций
- Четкое разделение ответственности
- Будущее извлечение пакетов в отдельные репозитории
- Параллельная командная разработка разных пакетов
- Переиспользуемые компоненты по всей платформе

### 2. Полнофункциональный GDScript
Как клиентские, так и серверные компоненты написаны на GDScript, обеспечивая:
- Согласованный язык и паттерны во всем стеке
- Совместное использование кода между клиентом и сервером
- Упрощенный рабочий процесс разработки
- Нативную интеграцию с Godot

### 3. Организация на основе пакетов (ОБЯЗАТЕЛЬНО)

Следуя паттерну монорепозитория из Universo Platformo React, адаптированному для нативной системы аддонов Godot:
- **ВСЕ пакеты ДОЛЖНЫ быть в директории `packages/`** - без исключений
- Фронтенд (`-frt`) и сервер (`-srv`) ДОЛЖНЫ быть отдельными пакетами
- Базовая реализация ДОЛЖНА быть в поддиректории `base/` внутри каждого пакета
- Общий код ДОЛЖЕН быть в выделенных пакетах (например, `packages/universo-types`, `packages/universo-utils`)
- Каждый пакет является самодостаточным плагином Godot с `plugin.cfg` и `plugin.gd`

**Соглашение об именовании пакетов**:
- Фронтенд-пакеты: `packages/{feature}-frt/base/`
- Бэкенд-пакеты: `packages/{feature}-srv/base/`
- Общие пакеты: `packages/{name}/base/` (для типов, утилит и т.д.)

**Будущая миграция**: Отдельные пакеты будут извлечены в отдельные репозитории по мере созревания проекта. Текущая структура монорепозитория облегчает начальную разработку, готовя к будущей распределенной архитектуре.

### 4. Расширяемость прежде всего
Паттерн директории `base/` позволяет:
- Множественные реализации одной функции
- Легкую миграцию технологического стека
- Архитектуру на основе плагинов
- Расширения от третьих сторон

## Основные компоненты

### Автозагрузки (Глобальные менеджеры)

#### Config
- **Назначение**: Централизованное управление конфигурацией
- **Местоположение**: `scripts/autoload/config.gd`
- **Обязанности**:
  - Загрузка конфигурации из `config.json`
  - Управление переменными окружения из `.env`
  - Предоставление флагов функций
  - Управление настройками времени выполнения

#### DatabaseManager
- **Назначение**: Абстракция операций с базой данных
- **Местоположение**: `scripts/autoload/database_manager.gd`
- **Обязанности**:
  - Подключение к Supabase
  - Выполнение CRUD-операций
  - Обработка ошибок базы данных
  - Управление состоянием подключения
- **Будущее**: Поддержка множественных бэкендов баз данных

#### NetworkManager
- **Назначение**: Многопользовательский режим и сетевое взаимодействие
- **Местоположение**: `scripts/autoload/network_manager.gd`
- **Обязанности**:
  - Создание и управление сервером
  - Клиентские подключения
  - Пиринговая коммуникация
  - Обработка RPC
  - Управление состоянием сети

## Архитектура пакетов

> **⚠️ КРИТИЧЕСКОЕ ТРЕБОВАНИЕ**: ВСЯ реализация функций ДОЛЖНА происходить внутри пакетов в директории `packages/`. Единственные исключения:
> - `project.godot` - конфигурация проекта Godot
> - `scenes/` (корень) - ТОЛЬКО главные сцены входа приложения (НЕ сцены функций)
> - `scripts/` (корень) - ТОЛЬКО скрипты автозагрузки/синглтонов для глобальных сервисов
> - Скрипты сборки и запуска в корне репозитория
>
> Логика функций, UI, модели данных и бизнес-логика ДОЛЖНЫ быть в соответствующих пакетах. Нарушение этого требования компрометирует модульную архитектуру проекта и будущую поддерживаемость.

### Структура пакета

Каждый пакет функции следует этой структуре:

```
packages/{feature}-{type}/base/
├── scenes/              # Сцены Godot (.tscn)
├── scripts/             # Файлы GDScript (.gd)
├── resources/           # Ресурсы Godot (.tres, .res)
├── assets/              # Ресурсы, специфичные для функции
├── api/                 # Конечные точки REST API (только сервер)
├── plugin.cfg           # Метаданные плагина
├── plugin.gd            # Точка входа плагина
├── README.md            # Документация (английский)
└── README-RU.md        # Документация (русский)
```

### Типы пакетов

#### Пакеты фронтенда (`-frt`)
- **Назначение**: Клиентский UI и логика
- **Содержит**:
  - UI-сцены и компоненты
  - Клиентские модели данных
  - Обработчики взаимодействия пользователя
  - Управление локальным состоянием
- **Пример**: `packages/clusters-frt/`

#### Серверные пакеты (`-srv`)
- **Назначение**: Серверная логика и API
- **Содержит**:
  - Бизнес-логика
  - Конечные точки API
  - Валидация данных
  - Операции с базой данных
  - Серверное состояние
- **Пример**: `packages/clusters-srv/`

#### Общие пакеты
- **Назначение**: Общий код, типы и утилиты, используемые в нескольких пакетах
- **Содержит**:
  - Общие модели данных и типы (например, `packages/universo-types/`)
  - Утилитарные функции (например, `packages/universo-utils/`)
  - Общие ресурсы и активы (например, `packages/universo-resources/`)
  - Общая логика валидации
  - Общие константы и перечисления
- **Соглашение об именовании**: Используйте описательные имена без суффиксов `-frt` или `-srv`
- **Пример**: `packages/universo-types/base/`
- **Лучшая практика**: Создавайте общие пакеты заранее, когда сущности/утилиты нужны 2+ пакетам

**Справка**: См. [Universo Platformo React](https://github.com/teknokomo/universo-platformo-react) для примеров паттернов общих сущностей и организации пакетов.

### Паттерны коммуникации

#### Коммуникация Клиент ↔ Сервер

1. **В реальном времени (Multiplayer API)**:
   ```gdscript
   # Клиент отправляет
   NetworkManager.send_to_server(data)
   
   # Сервер получает через RPC
   @rpc("any_peer")
   func handle_client_request(data):
       pass
   ```

2. **HTTP REST API** (Будущее):
   ```gdscript
   # Клиент делает HTTP-запрос
   var http = HTTPRequest.new()
   http.request("https://api/clusters")
   
   # Сервер обрабатывает через конечную точку REST
   func handle_get_clusters(request):
       return clusters_data
   ```

#### Коммуникация Пакет ↔ Пакет

1. **Сигналы** (Событийно-ориентированные):
   ```gdscript
   # Пакет A генерирует
   signal resource_updated(resource_id)
   
   # Пакет B подключается
   PackageA.resource_updated.connect(_on_resource_updated)
   ```

2. **Прямые вызовы** (Когда уместно):
   ```gdscript
   var cluster_manager = ClusterManager.new()
   var result = cluster_manager.get_cluster(id)
   ```

3. **Доступ через автозагрузку** (Глобальное состояние):
   ```gdscript
   var db_connected = DatabaseManager.is_connected
   NetworkManager.send_to_all(data)
   ```

## Поток данных

### Типичный поток запроса

1. **Взаимодействие пользователя** → UI-сцена
2. **UI-событие** → Скрипт пакета фронтенда
3. **Сетевой запрос** → NetworkManager
4. **Сервер получает** → Серверный пакет
5. **Бизнес-логика** → Скрипты серверного пакета
6. **Операция с БД** → DatabaseManager → Supabase
7. **Ответ** → Сеть → Клиент
8. **Обновление UI** → Пакет фронтенда → Сцена

### Управление состоянием

#### Клиентское состояние
- Локально для каждого клиента
- Управляется пакетами фронтенда
- Синхронизируется через NetworkManager

#### Серверное состояние
- Авторитетное состояние игры
- Управляется серверными пакетами
- Сохраняется в базе данных

#### Общее состояние
- Конфигурация (автозагрузка Config)
- Статус сети (NetworkManager)
- Подключение к БД (DatabaseManager)

## Архитектура сети

### Модель клиент-сервер

```
Множество клиентов ← → Единый авторитетный сервер ← → База данных
```

### Сетевые режимы

1. **Режим сервера** (Без графики):
   - Без рендеринга
   - Авторитетная логика
   - Управление состоянием
   - Операции с базой данных

2. **Режим клиента**:
   - Полный рендеринг UI
   - Обработка пользовательского ввода
   - Предсказание локального состояния
   - Синхронизация с сервером

3. **Автономный режим**:
   - Локальная разработка
   - Тестирование в одиночном режиме
   - Сеть не требуется

## Архитектура базы данных

### Текущая: Supabase

- База данных PostgreSQL
- Доступ через REST API
- Подписки в реальном времени
- Аутентификация

### Паттерн схемы базы данных

У каждой функции свои таблицы:

```sql
-- Система кластеров
clusters (id, name, description, created_at, updated_at)
domains (id, cluster_id, name, type, created_at, updated_at)
resources (id, domain_id, name, data, created_at, updated_at)

-- Система метавселенных
metaverses (id, name, description, created_at, updated_at)
sections (id, metaverse_id, name, data, created_at, updated_at)
entities (id, section_id, type, data, created_at, updated_at)
```

### Будущая поддержка баз данных

DatabaseManager разработан для поддержки множественных бэкендов:
- PostgreSQL (прямой)
- MongoDB
- SQLite (локальный)
- Другие облачные базы данных
